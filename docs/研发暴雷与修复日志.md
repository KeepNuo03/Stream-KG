### [R-001] 对话回答粗糙：高频“根据已有资料无法回答”
- **发现时间**：2026-06-11
- **发现方式**：用户多轮对话观察；同类问题反复以“无法回答”开头。
- **现象**：
  - 对相关问题也频繁给出“无法回答”；
  - 回答策略过于保守，体验上像“拒答机器人”。
- **影响范围**：
  - P1 核心价值（可用问答）受损；
  - Demo 汇报时观感差，难以体现 RAG 价值。
- **根因**：
  1. Prompt 指令过于刚性，显式强化“上下文不足就无法回答”；
  2. 无检索质量门控，低质量或乱码 chunk 也进入生成；
  3. 引用兜底策略过硬（无引用时强制补 `[1]`），放大“模板味”。
- **修复方案**：
  1. **Prompt 改写**：从“优先拒答”改为“优先给有帮助结论，仅在明显不相关时拒答”；
  2. **检索质量门控**：新增 `RAG_MIN_RELEVANCE_SCORE` 与 `RAG_LOW_RELEVANCE_MARGIN`；
  3. **上下文可用性过滤**：过滤明显乱码 chunk（替换符比例/可读字符比例）；
  4. **引用策略调整**：无引用时不再强制改写正文补 `[1]`；
  5. **可观测性增强**：SSE 返回 `top_score/raw_chunk_count`，前端展示检索元信息。
- **验证结果**：
  - 非相关 query 会触发“低相关性提示”而非直接幻觉回答；
  - 相关 query 不再被固定模板强制压成“无法回答”首句；
  - 可在前端直接看到检索质量指标，便于定位问题位于“检索”还是“生成”。
- **后续动作**：
  - 对历史已入库 PDF 做一次重处理（新解析策略）；
  - P2 引入 reranker 后复核阈值。

### [R-002] PDF 入库后文本乱码，导致问答质量下降
- **发现时间**：2026-06-10
- **发现方式**：文档 chunk 与回答内容出现大量乱码字符（`�`）。
- **现象**：
  - 文档状态显示 `ready`，但检索文本可读性极差；
  - 对话经常“无法回答”或输出乱码信息。
- **影响范围**：
  - 检索命中但不可读，直接拖垮问答质量；
  - 易误判为 LLM 问题，增加排障成本。
- **根因**：
  - pypdf 快速提取对部分中文 PDF 字体映射不友好，输出乱码；
  - 原流程“只要提取非空就返回”，未做文本质量校验。
- **修复方案**：
  - 对 pypdf 提取结果新增可读性判定，低质量文本不入库；
  - 低质量时自动回退 MinerU 进行高质量解析。
- **验证结果**：
  - 新导入文档可显著降低乱码落库概率；
  - 检索上下文可读性提升，回答质量更稳定。
- **后续动作**：
  - 增加“文档质量评分”字段，支持后台观测。

### [R-003] 聊天前端“卡住不出字”：SSE 分包兼容问题
- **发现时间**：2026-06-10
- **发现方式**：前端气泡长期显示 `...`，后端日志显示接口 200 正常。
- **现象**：
  - 后端有 token/done 事件；
  - 前端未正确消费事件，持续发送中。
- **影响范围**：
  - 对话功能体感不可用。
- **根因**：
  - 前端仅按 `\n\n` 拆 SSE 包，未兼容 `\r\n\r\n`。
- **修复方案**：
  - 解码后统一换行符（`\r\n -> \n`）再解析；
  - `done/error` 事件后主动取消 reader；
  - 增加历史回捞兜底，避免空白气泡。
- **验证结果**：
  - token、citation、done 均可被前端稳定消费；
  - 发送状态可正常收敛。
- **后续动作**：
  - 增加前端 SSE 解析单测（CRLF/LF 两种流）。

### [R-004] 首 token 延迟高：Embedding 服务不可用导致超时等待
- **发现时间**：2026-06-10
- **发现方式**：首 token 延迟长期 >20s，排查发现 8081 未监听。
- **现象**：
  - 检索阶段先卡住，再进入生成；
  - 即使后端可答，也表现为“突然蹦一大段”。
- **影响范围**：
  - 流式体验差，误判为 LLM 慢。
- **根因**：
  - Embedding 服务未启动时，每次请求都等 30s 超时后才降级。
- **修复方案**：
  - 将 embedding 请求超时降到 2s；
  - 新增降级冷却窗口（60s），避免每次重复超时。
- **验证结果**：
  - 首 token 延迟从 ~30s 降至 ~9-10s（当前环境）。
- **后续动作**：
  - 启动本地 embedding 服务，目标进一步降至 3-5s。

### [R-006] PDF 解析任务失败/超时（Windows 环境）

- **发现方式**：文档持续 `failed`，终端出现 MinerU 相关异常。
- **现象**：
  - `MinerU CLI not found`、依赖冲突、模型下载慢、超时；
  - 子进程读取偶发 `gbk` 解码异常。
- **影响范围**：
  - PDF 入库不稳定，阻塞主流程。
- **根因**：
  - 依赖组合过重（`mineru[all]`）与网络环境不稳定；
  - Windows 下子进程编码差异；
  - 固定超时对首轮模型下载不友好。
- **修复方案**：
  - 切换 `mineru[pipeline]`；
  - 子进程改 `utf-8 + ignore`；
  - 解析超时改可配置；
  - 增加 pypdf 快速路径并与 MinerU 互补。
- **验证结果**：
  - 解析链路可稳定跑通；
  - 错误定位信息明显更清晰。
- **后续动作**：
  - 增加“首次模型预热”脚本，减少首跑失败。

### [R-008] 掘金 URL 导入后仅显示域名/等待页，问答答非所问
- **发现时间**：2026-06-11
- **发现方式**：用户导入 `juejin.cn/post/...` 后，文档标题显示为 `juejin.cn`，提问“链接里有啥”时回答混入无关内容。
- **现象**：
  - 解析正文只得到 `Please wait...`；
  - 文档卡片标题为域名，不是文章标题；
  - 对话检索混入历史文档，导致答非所问。
- **影响范围**：
  - 网页导入的核心价值下降；
  - Demo 场景下“链接问答”不可信。
- **根因**：
  1. 掘金详情页返回动态壳（前端渲染），通用 HTML 抽取拿不到正文；
  2. URL 导入初始标题使用 host，未在解析后回写真实标题；
  3. “问最新链接”意图缺少文档范围约束，检索可能混入历史脏数据。
- **修复方案**：
  1. `WebParser` 增加 `parse_with_meta()`，返回 `(正文, 标题)`；
  2. 对动态壳/反爬场景新增 reader 代理回退抓取（`https://r.jina.ai/<url>`）；
  3. 增加占位内容识别（如 `Please wait...`），避免落库为有效正文；
  4. Ingest 流水线在 web 文档解析成功后回写真实标题；
  5. 对话路由新增“最新链接意图”识别，命中时锁定最近一条 ready 的 web 文档 chunks。
- **验证结果**：
  - 同一掘金 URL 能抽取到有效正文（不再是 `Please wait...`）；
  - 新导入文档标题会更新为文章标题；
  - “看看我最新传入的链接里有啥”检索范围收敛到最新网页文档，不再混入历史旧文档。
- **后续动作**：
  - 对已入库的历史占位网页文档做一次清理或重处理；
  - 后续补“按 doc_id 对话”能力，彻底避免跨文档串扰。

### [R-009] 文档删除操作卡顿（点击后约 5 秒才返回）
- **发现时间**：2026-06-11
- **发现方式**：用户反馈“点删除卡半天”；接口压测复现。
- **现象**：
  - `DELETE /documents/{doc_id}` 稳定在 ~5s 级别；
  - 删除后列表刷新并不慢（几十 ms），卡顿主要发生在删除请求阶段。
- **影响范围**：
  - 单删/批删交互体验差；
  - 用户误以为前端卡死或删除失败。
- **根因**：
  1. 删除主链路同步等待 Qdrant 删除返回；
  2. 当前 Qdrant 客户端/服务端组合下，删除请求默认超时窗口导致单次调用约 5s；
  3. SQLite 删除本身很快（毫秒级），不是瓶颈。
- **修复方案**：
  1. 删除流程改为“主链路快速返回 + 向量后台 best-effort 清理”；
  2. 先删除 SQLite 文档与本地文件，再由后台任务异步清理 Qdrant points；
  3. 对后台向量清理失败仅记录告警日志，不阻塞用户请求。
- **验证结果**：
  - 删除接口平均耗时由 ~5078ms 降至 ~30ms；
  - 单删接口体感恢复“即时响应”；
  - 文档列表接口维持几十 ms，未引入额外退化。
- **后续动作**：
  - P2 图谱上线后，将图谱级联删除纳入同一异步清理编排并增加可观测指标；
  - 增加“后台清理状态”监控项（队列长度、失败次数、重试策略）。

### [R-010] P2 图谱有数据但前端空图 / API 返回 0 节点
- **发现时间**：2026-06-12
- **发现方式**：SQLite / `graph.pkl` 显示数百实体，但 `GET /graph` 返回 `node_count=0`；用户反馈「导入文档了没有图」。
- **现象**：
  - `FEATURE_KG_ENABLED=true`，`placeholder=false`，但 nodes/edges 为空；
  - 磁盘上 `graph.pkl` 已有 200+ 节点。
- **影响范围**：
  - P2 图谱可视化完全不可用；
  - 易误判为「KG 没跑」或「开关没开」。
- **根因**：
  1. **Ingest 与 API 使用两个 `GraphStore` 实例**：入库写一份内存图并 `persist` 到磁盘，API 单例在启动时若已初始化为空图，**不会重新读 `graph.pkl`**；
  2. 后端若先于 embedding 启动，健康检查显示 `embedding=unknown`（次要，不直接导致空图）。
- **修复方案**：
  1. `GraphStore` 在 `export_graph` 前按磁盘 `mtime` **热加载** `graph.pkl`；
  2. `IngestPipeline` 改为注入与 API 共用的 `get_graph_store()` 单例；
  3. 启动日志打印 `FEATURE_KG_ENABLED` 与 embedding 探活结果。
- **验证结果**：
  - 重启 Backend 后 `/graph` 可返回与 `graph.pkl` 一致的节点数；
  - 无需重导入即可看到历史图（展示层修复）。
- **后续动作**：
  - 单测覆盖「writer persist → reader export 热加载」；
  - 文档中注明：**先启 embedding，再启 backend**。

### [R-011] Embedding 走伪向量：检索随机、问答极烂、health 显示 `mode=pseudo`
- **发现时间**：2026-06-11 ~ 2026-06-12
- **发现方式**：Backend 启动告警「Embedding 未使用真实向量」；`http://localhost:8081/health` 为 `mode=pseudo`；用户反馈回答质量极差。
- **现象**：
  - embedding 服务进程在跑，但 `/health` 为 `pseudo`；
  - 日志大量 `huggingface.co` 连接超时 / `WinError 10061`；
  - 检索 TopScore 无意义，LLM 只能胡编或拒答。
- **影响范围**：
  - **P1 RAG 核心价值失效**（比「回答保守」更严重）；
  - 已入库 chunk/entity 向量全部为伪向量，**必须 reprocess** 才能恢复。
- **根因**：
  1. 国内网络无法稳定访问 HuggingFace，旧版 `embedding_server` 仅从 HF 拉 `Qwen/Qwen3-Embedding-0.6B`，失败后静默降级为**确定性伪向量**；
  2. 用户终端 `uv` 不在 PATH，embedding 服务曾长期未真正启动，Backend 侧也走客户端伪向量兜底；
  3. 伪向量与真实向量混用时期入库的数据，reprocess 前无法自动修复。
- **修复方案**：
  1. 默认 `EMBEDDING_DOWNLOAD_SOURCE=modelscope`，从 ModelScope 下载到 `data/models/`；
  2. 配置 `HF_ENDPOINT=https://hf-mirror.com` 作为 HF 回退；
  3. 支持 `EMBEDDING_MODEL_LOCAL_PATH` 指向已下载目录；
  4. `/health` 返回 `mode` / `error`，启动时预加载模型；
  5. Backend `probe_backend` 与启动告警联动。
- **验证结果**：
  - ModelScope 下载成功后 `mode=real`，向量维度 1024；
  - 路径示例：`data/models/Qwen/Qwen3-Embedding-0___6B`。
- **后续动作**（**操作清单**）：
  1. 先启 embedding，确认 `mode=real`；
  2. 再启 Backend，确认日志非 `pseudo`/`unknown`；
  3. **删除或 reprocess 所有在伪向量阶段导入的文档**；
  4. `.env` 可写 `EMBEDDING_MODEL_LOCAL_PATH` 跳过后续下载。

### [R-012] P2 图谱「又大又恶心」：噪声实体、mentions 乱链、页面卡顿、布局一直动
- **发现时间**：2026-06-12
- **发现方式**：用户截图：200 节点 / 191 边，标签为 `the/and/of/in` 等；图谱像长链蠕动；整页卡顿。
- **现象**：
  - 节点全是英文功能词，毫无语义；
  - 关系几乎全是 `mentions · conf 0.70`（旧数据）或相邻词共现链；
  - Cytoscape 力导向布局反复重算，选中节点也会触发布局；
  - 文档列表轮询频繁 `refreshGraph`，加重卡顿。
- **影响范围**：
  - P2 图谱 Demo 不可用，反向伤害产品观感；
  - 与「知识图谱」预期严重不符。
- **根因**：
  1. **C1 抽取过宽**：停用词不全（缺 `the/of/in/on` 等），短词 lowercase 仍入图；
  2. **C3 `mentions` 策略**：同 chunk 内按顺序两两连边 → 链状「虫子图」，边数爆炸；
  3. **展示未过滤**：API 默认 `limit_nodes=200`，含低频噪声节点；
  4. **前端**：`cose` 布局 + `selectedNodeId` 参与 effect → 反复 layout；200 节点渲染压力大。
- **修复方案**：
  1. 收紧 `EntityExtractor`（扩充停用词、纯小写≥6 字符、每 chunk≤12 实体）；
  2. API 默认 `limit_nodes=48`、`min_mentions=2`、`filter_noise=true`、`relation_type=semantic`（隐藏 mentions）；
  3. 每 chunk 最多 4 条边；`export_graph` 按标签过滤噪声节点；
  4. 前端默认「语义关系」、`grid` 静态布局、选中不重算布局、最多渲染 48 节点；减少轮询刷图。
- **验证结果**：
  - 刷新后节点数显著下降，布局静止，mentions 链默认隐藏；
  - **历史脏图仍会残留**，需删文档重导才能从根上干净。
- **后续动作**：
  - 清空旧图数据后重新导入学术论文类 PDF 验收；
  - P2 后续考虑 LLM 实体抽取或 NER，替代纯规则 C1；
  - 图谱区增加「需 reprocess 才有干净实体」的 UI 提示。

### [R-018] 元问题/浏览意图重构：「一共有几篇」走 SQLite，「看简历」只锁一份文档
- **发现时间**：2026-06-14
- **发现方式**：用户连测「一工有几篇文档」「你看一下简历」「一共有几篇文档」，前者吐简历 + 论文片段（证据兜底误用），后两个被 R-017 门控误拒或答非所问。
- **现象**：
  - 「一共有几篇文档」走 RAG 检索，把简历 chunk 和论文 chunk 一起塞进 LLM，输出「基于检索资料可先得到以下要点：- 程诺 简历… - dilated convolution…」；
  - 模型自己（在另一次问答中）发现「[3]/[4]、[5]/[6] 重复，可能来自同一文档」，说明 RAG 上下文里**根本不该有「文档总数」的问题**；
  - R-017 之后浏览意图全部走 `_BROAD_DOC_PATTERNS` 放宽阈值，反而把概念题也带进来。
- **影响范围**：
  - 用户多次反馈「随便一测就抽风 / 傻了直接」；
  - 资料库 RAG 看起来像 ChatGPT 乱编；
  - 隐私信息（简历）在无关问题下被展示。
- **根因**：
  1. **元问题（count/list）本质是元数据查询**，不该走向量检索；
  2. **浏览意图（看简历 / 看刚导入的文档）应锁定一份文档**，混入 top-k 会把论文文本贴成「简历总结」；
  3. R-017 把所有「浏览/元问题」都塞进 `_BROAD_DOC_PATTERNS` 放宽 gate，导致概念题/浏览题/简历题边界混淆；
  4. 证据兜底未做「词面命中」二次校验，只要有 chunk 就敢贴。
- **修复方案**：
  1. 新增 `stream_kg/retrieval/meta_query.py`：
     - `detect_meta_intent` → `count` / `list` 直接基于 SQLite `list_documents()` 构造答案，**跳过向量检索与 LLM**；
     - `resolve_browse_target` → 简历/最新文档/最新链接 → 唯一目标文档；
     - `build_locked_chunks` → 仅返回该文档的可用 chunk。
  2. `api/routes/chat.py` 流程：先元问题直答，再浏览锁定（跳过 gate 与证据兜底），最后才走普通向量检索；
     - SSE `retrieval` 事件新增 `retrieval_source`（`meta:count` / `browse:resume` / `vector`）、`locked_doc_title`；
  3. `relevance_gate.py` 清理 `_BROAD_DOC_PATTERNS`：移除「简历 / 导入 / 资料库」等浏览类，只保留真正的「讲了什么 / 总结一下」；
  4. `should_use_evidence_fallback` 收紧：广问 + 无词面命中 + 概念题 → 永不走兜底；
  5. 前端检索元信息条改版：用 chip 形式展示 `元数据直答 / 锁定文档 · <title> / 向量检索 · <mode>`，并显示 overlap / top / reason，便于自测与 demo。
- **涉及文件**：
  - 新增：`stream_kg/retrieval/meta_query.py`、`tests/unit/test_meta_query.py`
  - 修改：`api/routes/chat.py`、`stream_kg/retrieval/relevance_gate.py`、`frontend/src/app/page.tsx`、`tests/unit/test_relevance_gate.py`、`tests/unit/test_graph_store_reload.py`
- **验证结果**：
  - 全部单测通过（33 项）；
  - 「一共有几篇文档」→ SQLite 直答，给出总数 + 已就绪数 + 示例标题；
  - 「你看一下简历」→ 若存在标题含「简历」的文档则锁定总结，否则提示「未找到简历类文档」，不再混入论文；
  - 「知识图谱是什么」→ 仍拒答（无相关资料）；
  - 「程诺的求职目标是什么」→ 正常答（人名命中）。
- **后续动作**：
  - 重启 backend + 刷新前端；
  - demo 时检索元信息条可直接展示走的是哪条路径；
  - 标题没含「简历」二字的简历文档需手动重命名，或后续做基于内容的 doc_kind 推断。

### [R-017] 问「知识图谱是什么」却吐出简历 + 论文碎片（误感「模型抽风」）
- **发现时间**：2026-06-12
- **发现方式**：用户反馈「模型不经测啊，我随便一测就抽风了」；提问 **「知识图谱是什么」**。
- **现象**：
  - 未解释「知识图谱」定义，而是输出模板：「基于当前检索到的资料可先得到以下要点：」；
  - Bullet 1：简历个人信息（姓名程诺、年龄 22、邮箱电话、求职方向、莱斯大学教育背景等）`[1]`；
  - Bullet 2/3：论文技术句摘录（dilated convolution、feature extraction、inference…）`[2][3]`；
  - 结尾：「以上为证据摘录式总结，若需要更完整结论，建议补充同主题文档。」
- **用户体感**：像 LLM 胡编或「抽风」；实际是 **RAG 误检索 + 拒答后证据保底** 叠加。
- **影响范围**：
  - 资料库 RAG 产品边界被误解为「通用百科」；
  - 隐私敏感内容（简历）可能在无关问题下被展示；
  - Demo 随手测概念题极易翻车。
- **根因**：
  1. `RAG_MIN_RELEVANCE_SCORE=0.03` 过低，弱相关 chunk 仍进入生成链路；
  2. 资料库无「知识图谱」主题，向量检索仍会弱命中简历 / 论文 chunk；
  3. LLM 判断应拒答（正确），但 `chat.py` 在识别拒答后 **无条件** 调用 `build_evidence_fallback_answer`，把 top chunk 硬贴为「要点」；
  4. 缺少 **词面重叠** 校验，无法识别「问题词未出现在任何 chunk 中」。
- **修复方案**：
  1. 新增 `stream_kg/retrieval/relevance_gate.py`：向量分 + 词面重叠双门控；
  2. 默认 `RAG_MIN_RELEVANCE_SCORE=0.38`、`RAG_LOW_RELEVANCE_MARGIN=0.04`；
  3. 证据保底仅当 `RAG_EVIDENCE_FALLBACK_MIN_SCORE=0.48` 且词面相关时启用（`should_use_evidence_fallback`）；
  4. 无词面重叠时返回：「资料库中没有与问题直接相关的内容…请补充相关文档」；
  5. SSE `retrieval` 事件增加 `lexical_overlap`、`retrieval_reason` 便于前端观测。
- **涉及文件**：
  - `stream_kg/retrieval/relevance_gate.py`（新增）
  - `api/routes/chat.py`
  - `stream_kg/config.py`、`.env.example`
  - `tests/unit/test_relevance_gate.py`
- **验证结果**：
  - 单测：`test_knowledge_graph_query_rejected_without_overlap` 等 3 项通过；
  - 修复后「知识图谱是什么」应提示缺资料，不再贴简历。
- **后续动作**：
  - **重启 Backend** 后复测；
  - 汇报/demo 避免用「资料库外的通用概念题」验收 RAG（应说明「仅基于已导入资料」）；
  - 若正常文档问题被误拒，微调 `RAG_MIN_RELEVANCE_SCORE`（勿回退到 0.03）。
- **产品说明（对外口径）**：本产品是 **个人资料库问答**，不是 ChatGPT 式通识；无关问题应拒答或引导导入文档，而非贴随机检索片段。
- **回归（R-017b，同日）**：修复后「程诺的求职目标」也被误拒——词面抽取把整句当成一个词、错误文案硬编码「知识图谱」。已改为按「的」分词 + 子词扩展，且 **至少 1 个查询词命中 top chunk** 即放行；提示语改为通用表述。
- **回归（R-017c，同日）**：「你看一下简历」「看一下导入的文档」仍被拒——元指令不含实体词，向量分低 + 词面无重叠。已增加 `_is_browse_doc_intent` 锁定目标文档 chunk；泛化浏览类问题（含简历/导入）放宽向量阈值。

## 阶段性结论（Phase 1）

- P1 功能链路已基本闭环（导入 -> 检索 -> 对话 -> 引用）。
- 关键风险从“功能不可用”转向“质量稳定性与可观测性”。
- 后续优先级建议：**回答质量 > 性能优化 > 新功能扩展**。

## 阶段性结论（Phase 2 图谱，2026-06-12）

- **图谱≠能画出来就行**：规则 C1 + mentions 共现边在论文 PDF 上极易退化为「停用词链」，必须过滤展示 + 收紧抽取 + 重导数据。
- **向量质量是 RAG 前置条件**：`mode=pseudo` 时图谱与问答都不可信；国内环境默认 ModelScope，且伪向量阶段数据必须 reprocess。
- **多实例图存储是隐形 bug**：写盘与读 API 不同步会导致「库里有图、页面没有」。
- 推荐启动顺序：**embedding（real）→ backend → frontend**；图谱验收前务必 **删旧文档重导**。
- **问答与图谱已分叉验收（R-016）**：本轮用户反馈「问答好多了、图谱仍不行」符合预期——**真实 embedding + 重导**直接修复 RAG；图谱受规则抽取上限制约，展示/过滤只能缓解，不能替代 C1/C3 升级。

## 阶段性结论（Phase 4 Agent，2026-06-14）

- **RAG 单轨已到天花板（R-017 / R-018）**：继续在 `meta_query` / `relevance_gate` 上堆规则无法解决「像真人聊天」与「不乱编」的双重目标；典型反例包括概念题贴简历、元问题乱答、闲聊被冷拒答（「我现在传文档 一会儿问你」）。
- **MVP 阶段策略**：P1–P3 以「能演示、能问答、有图谱」为主，**不再深入 Agent 化**；临时规则（元问题直答、浏览锁文档、门控）仅作止血。
- **正式路线已规范化**：详见 [spec/12-agent-roadmap.md](spec/12-agent-roadmap.md) — Router + Tool-Calling + 会话状态 + 分阶段 P4.0–P4.4。

## R-019 阈值过严 + 标题驱动简历识别失败 + 小语料图谱被滤空（2026-06-14）

### 现象

接 R-018 修复后的真机验证（导入「程诺_研0gap_日常实习.pdf」+「Attention Is All You Need.pdf」），6 条测试 query 几乎全崩：

| Query | 预期 | 实际 |
|---|---|---|
| 一共有几篇文档 | meta:count 直答 | ✅ 正常 |
| 你看一下简历 | browse:resume 锁定简历 | ❌ 走向量 → 冷拒答 |
| 程诺的求职目标是什么 | 命中简历回答 | ❌ 冷拒答（reason: low_vector_score） |
| 知识图谱是什么 | 冷拒答（资料库无） | ✅ 冷拒答（预期内） |
| 我现在传文档 一会儿问你 | 闲聊承接 | ❌ 冷拒答（MVP 接受，P4 修） |
| Transformer 的自注意力是怎么计算的 | 命中 attention 论文 | ❌ 冷拒答（reason: low_vector_score） |

同时**知识图谱页面完全空白**（"暂无图谱节点"），但 `graph.pkl` 实际有 N KB 数据。
`http://localhost:8081/health` 确认 `mode=real`。

### 根因

三个独立问题同时引爆，互不相关：

1. **门控阈值过严**（主因，6 条中崩 3 条）：`rag_min_relevance_score=0.38` 是按某次离线验证拍的，Qwen3-Embedding-0.6B 在中文混合段落召回时的实际 cos 经常落在 0.20–0.35。"Transformer 自注意力"对 attention 论文这种"教科书级匹配"都过不去，等于把门焊死。
2. **简历靠标题识别**（崩 1 条）：用户的简历文件名是 `程诺_研0gap_日常实习.pdf`，标题不含「简历/resume/cv」任何关键词。`resolve_browse_target` 只匹配标题，必然返回 `None` → 走 vector → 又被阈值挡。
3. **图谱 `min_mentions=2` 在小语料下零节点**：只导入 2 份文档时，绝大多数实体每个文档只 mention 1 次，硬卡 ≥2 直接把池子清空 → 连通子图返回 0 节点 → 前端"暂无图谱节点"。

三个问题的共同特征：**单独看每条规则都合理，组合在「2 文档 + 中文跨段落」场景下集体失效**。

### 修复

| 文件 | 改动 |
|---|---|
| `stream_kg/config.py` | `rag_min_relevance_score: 0.38 → 0.20`；`rag_evidence_fallback_min_score: 0.48 → 0.30`；`rag_low_relevance_margin: 0.04 → 0.05` |
| `stream_kg/retrieval/meta_query.py` | 新增 `looks_like_resume_text(text)`（5 组关键词，命中≥2 组即简历）和 `resolve_browse_target_with_samples(..., head_text_by_doc=...)`：标题失败时按首段 chunk 内容兜底 |
| `api/routes/chat.py` | 简历意图但标题匹配失败时，预取每份 ready 文档前 3 段 chunk，调用 `resolve_browse_target_with_samples` |
| `stream_kg/kg/graph_store.py` | `export_graph` 自适应：`min_mentions=2` 滤完为空时，自动降到 1，再降到 1（兜底）；返回 `stats.applied_min_mentions` 暴露真实取值 |

### 经验

1. **绝对阈值要绑模型**：把 `rag_min_relevance_score` 写死成数字是典型反模式。应该按 embedding 模型在该业务上的实测分位（如 P30 / P50）来取，并在 `.env` 里可调。本次留作 P3 优化项。
2. **「按标题判类型」是简历类文档的暗坑**：用户文件名千奇百怪（求职版本号、岗位代号、HR 二改），靠标题命中等同碰运气。**必须用内容启发式**作主路径之一。同理：发票/合同/论文/财报都该有内容签名。
3. **过滤参数要按语料规模自适应**：`min_mentions=2` 在 100 篇语料下是去噪，在 2 篇语料下是清零。任何"硬过滤阈值"都该有 fallback 链。
4. **复盘陷阱**：R-017 / R-018 解决"乱编"时把门控拉到 0.38 自我安慰；R-019 是回旋镖。**每次抬门控阈值都要补一组反向测试 query**（确保真该命中的能进来）。

### R-019 附录：诊断中发现的「假修复」陷阱（2026-06-14 晚补）

把阈值降到 0.20 后前端仍然全崩，进一步追踪发现真正的隐藏根因不是阈值，而是 **embedder 熔断 + 历史 pseudo 向量残留** 双杀：

| 现象 | 根因 |
|---|---|
| `top_score` 持续在 0.05–0.07 | Qdrant 里大部分 chunk 向量是 R-011 时期残留的 pseudo（确定性哈希向量），与 real query 向量空间正交 |
| 重启 backend 后偶发好偶发坏 | embedder 客户端在任何 HTTP 异常下都触发 60s 熔断窗口，期间所有 query 都走 `_deterministic_vector` 伪向量 |
| 简单一段长文本就把 embedder 击穿 | `embedding_request_timeout_sec=2.0` 太短，CPU 推理 Qwen3-0.6B 单段 0.5–5s，第一次/长段必 timeout |
| Qdrant 客户端 1.18 vs 服务端 1.14 警告 | 实测兼容（search/retrieve 都能跑），但版本不一致是隐患，已锁 `qdrant-client<1.15` |

**诊断脚本是关键**：`scripts/diagnose_rag.py` 用 7 个由浅入深的探测点（config 阈值 / `/health` / `/embed` 直连耗时 / vector_search top_score / stored vs fresh cos / 自检索 / 直连 Qdrant / stored 向量回搜 / embedder 一致性）把 4 个嫌疑都排查了一遍。**关键证据**：[5e] stored→stored cos=1.0（Qdrant 索引没坏） + [5f] embedder 5 次同文本完全一致但 mode=client_pseudo（embedder 在熔断窗口） + [5b] 历史误判 cos=1.0 是因为两边都是 pseudo（同 hash 命中）。

**真修复**：
- `pyproject.toml`：`qdrant-client>=1.14,<1.15`
- `.env` + `config.py`：`embedding_request_timeout_sec` 2 → 60；`embedding_fallback_cooldown_sec` 60 → 5
- `stream_kg/encoding/embedder.py`：只在 `ConnectError/ConnectTimeout` 触发熔断窗口；HTTP 4xx/5xx 仅本次降级，不锁后续请求
- `scripts/reset_all_data.py`：一键清空 Qdrant collection + SQLite + graph.pkl，强制重建为正确状态
- 操作上：清空后重新上传所有文档，让 chunk 向量都是新生 real 向量

**经验**：
- 「`/health` 显示 mode=real」 不等于 「所有向量都是 real」，**stored 是否 real 必须用「同文本 fresh embed vs stored embed cos」单独验证**，否则历史脏数据会持续污染检索分。
- 熔断对「服务真断」有用，对「单次 HTTP 错误」是反模式 —— 后者不应让整个进程的 query 链路在 X 秒内全部哑火。
- 任何带降级 fallback 的客户端，**fallback 期间的状态必须能从 `/health` 之外的渠道暴露**（比如返回里塞 `client_mode=pseudo` 头），否则上层永远不知道自己在用垃圾向量。

### 速查表新增

| 现象 | 排查 |
|---|---|
| 所有 query 都"相关性较低"且 embedding=real | `rag_min_relevance_score` 是否被设到 0.3+；查 retrieval chip 的 `top` 数值 |
| 「看一下简历」走向量 | 文件标题是否不含简历关键词 → 走内容启发式 |
| 图谱页面空 + `graph.pkl` 有内容 | `min_mentions` 是否过严；`stats.applied_min_mentions` 是否已降至 1 |
| 导入很少（≤3 篇）图谱稀 | 是设计取舍：边数本来就少；展示侧加引导文案而非降置信度 |

## R-020 · 图谱抽取器全面重写：从「永远 create + 固定 0.6」到「确定性合并 + 共现累加」（2026-06-15 凌晨）

### 现象

P3 UI 收尾后跑 `/api/v1/graph`，返回空。但 `/api/v1/stats` 显示 138 实体 / 64 条边。
深挖 `graph.pkl`：

```text
nodes: 138, edges: 64
mention_count distribution: [(1, 138)]      # ← 全是 1
relation type counts: [('mentions', 64)]    # ← 全是 mentions
confidence stats: min 0.6, max 0.6, avg 0.6 # ← 全是 0.6
sample noise nodes: Provided / Google / News / Calling / Schema / Pydantic / Redis / proper / Working ...
```

导出器门控（`min_mentions_conf=0.68`）→ 64 条边全部被一刀切死 → 没连通节点 → 空图。

### 根因（三层叠加）

1. **OnlineResolver 永远 create**：
   - `resolve_threshold = 0.82`，composite_score 公式权重和达 1.20，理论极限 1.20。
   - 但同名实体两次 embedding 上下文不同，cosine 不会精确 1.0，复合分常 < 0.82。
   - 结果：同一个 surface（Attention）每次出现都被 create 成新 entity_id，
     `mention_count` 永远是 1，TemporalExtractor 看到的也全是「两个独立 entity 相邻」=mentions。
2. **TemporalExtractor 没有共现累加**：
   - 每对相邻 mention 一律产 1 条 confidence=0.6 的边，写进 multi-edge graph 时
     用 `edge_id` 作为 key，所以同样关系也被存了 N 次但每条都是单次值。
3. **抽取器噪声过滤太宽**：
   - 任何长度 >= 4 且大小写混合的英文 token 都进，导致 `Provided` / `Google` / `News` /
     `Schema` 等噪声词全部入图。

### 修复

| 文件 | 修法 |
|------|------|
| `stream_kg/encoding/entity_extractor.py` | 1) 新增 `_ENGLISH_NOISE_TOKENS` 黑名单（70+ 词，覆盖 Provided/Google/Pydantic/various/...）；2) 新增 `canonicalize_label`：NFKC + lowercase + strip 标点；3) 新增 `derive_entity_id(canonical, type) -> hash`：相同 canonical+type 必同 ID；4) 新增 `infer_entity_type`：person/method/concept 粗粒度规则；5) `_is_valid_surface` 接入新黑名单，纯小写英文从 5 字符提到 6 字符；6) `is_displayable_entity_label` 同步过滤噪声词。 |
| `stream_kg/pipeline/ingest_pipeline.py` | `_run_incremental_kg` 重写：抛弃 OnlineResolver 的 vector composite_score 路径，直接用 `derive_entity_id` 打 deterministic ID；同名实体（含跨文档）自然合并，`mention_count` 真正可累加。原 ResolveResult 改为简单构造 `action=create/merge`，保留 vector 写入 entities collection（候选检索能力仍在，只是不再用于消解决策）。 |
| `stream_kg/kg/temporal_extract.py` | 1) 新增 proposes/introduces 等模板加入 `extends` 关系；2) 改写 `extract`：对全 chunk 内实体对做共现（窗口 5），同 (head, tail, rel) 累加 `count` 和 `evidence_chunks`；3) 新增 `_aggregate_confidence`：mentions 类按 `log(count+1) * 0.12` 累加，跨 chunk +0.05，封顶 0.92；4) mentions 对称归一（按 entity_id 字典序）避免重复计数。 |
| `stream_kg/kg/graph_store.py` | `add_temporal_edge` 改为 upsert：multi-edge key 从 `edge_id` 改为 `relation_type`，同 (head, tail, rel) 重复出现合并 evidence_count + 取较大 confidence + 累积 evidence_chunks 列表。`_build_connected_export` 的 `min_mentions_conf` 从 0.68 → 0.55，移除「必须 technical 端点」硬性要求（噪声过滤已上移到 `_select_node_pool`）。 |

### 关键设计取舍

- **为什么放弃向量消解**：向量消解需要 (a) entities collection 真实有效 (b) 阈值精调 (c) 同名实体上下文向量分布稳定。三条都不容易满足，对 MVP 性价比太低。确定性 ID 一次性解决「同名拆裂」问题，符合"先做对，再做好"原则。
- **为什么 mentions 边对称归一**：mentions 表达的是「共现」，本身无方向；不归一会让 (A→B) 和 (B→A) 各累计一半，confidence 永远到不了阈值。
- **为什么保留 OnlineResolver 不删**：未来 P4 LLM 抽取上线后，向量消解 + composite_score 仍是合理的辅助手段（处理别名/缩写/翻译同义）。删了反而要回写，留着低成本。

### 验证步骤

```powershell
# 1) Ctrl+C backend
# 2) uv run python scripts/reset_all_data.py --yes
# 3) 重启 backend
# 4) 前端重新上传两份 PDF
# 5) curl http://localhost:8000/api/v1/graph?min_mentions=2&max_nodes=80
#    预期：30-50 节点，20-40 条边，confidence 0.55-0.92 区间分布
```

### 教训

- 「向量+复合分」式实体消解听起来漂亮，但对小语料、相似上下文、缺少 alias 字典的场景非常脆弱。MVP 阶段应当先用规则把 80% 拿下来，再用向量补 20% 难例。
- 图谱抽取的 confidence 必须有「累积」语义，而不是单次 hit 的瞬时值。共现次数 / 跨 chunk 一致性是最廉价的真实信号。
- 节点过滤要在导出 *之前* 完成（pool 阶段），而不是在边过滤里靠 technical 判定卡。否则容易整张图被一道 if 切空。

### [R-022] Phase A.0 PoC 脚本在 PowerShell 上 UnicodeEncodeError
- **发现时间**：2026-06-15（Phase A.0 PoC 首次执行）
- **发现方式**：`scripts/test_kg_extract.py` 首跑 exit code = 1，`print(f"...¥{cost:.4f}")` 抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\xa5'`
- **现象**：
  - Python 脚本能正常返回 DeepSeek 结果（实际 PoC 数据完整）
  - 但 summary 阶段一旦 print 中 `¥` / 中文，立即栈崩
  - PowerShell 渲染层另外把"基于解析成功的样本"这种字符串显示为 "(基于解析成功的样�?"
- **影响范围**：
  - 所有走 PowerShell 终端的 Python 脚本（Windows 默认 stdout encoding = cp936/gbk）
  - 影响 Phase A.0 PoC 的报告输出可读性，未影响数据本身
- **根因**：
  - Python 3 在 Windows 上 `sys.stdout` 默认沿用系统 ANSI codepage（中文版 = cp936/gbk）
  - gbk 不含 `¥ (U+00A5)`、`±`、emoji 等字符
  - `response_format=json_object` 模式的 DeepSeek 返回是 UTF-8，写文件正常，但 `print` 走 stdout 触发编码失败
- **修复方案**：
  - 脚本顶部强制 `sys.stdout.reconfigure(encoding="utf-8")` + 同理 stderr
  - 把 stdout 里的 `¥` 改成纯 ASCII 文本 `CNY`
  - 关键报告产物用 `--save-md` 落文件，避开 PowerShell 渲染层的字体局限
- **验证结果**：
  - `--runs 3` 6 次调用全部 exit code = 0
  - markdown 报告 `docs/planning/_kg_poc_report.md` 用 UTF-8 写盘，VSCode/Cursor 显示完美
  - 已整合到 `docs/planning/14-kg-llm-execution-plan.md §10`
- **后续动作**：
  - 后续所有新增 Python 脚本（Phase A 的 `llm_extractor.py` 调用入口、Phase B 的 `reset_kg.py`、Phase E 的 `inspect_kg_extraction.py`）统一加 `reconfigure(encoding="utf-8")` 头部
  - 考虑抽出 `scripts/_utils/encoding.py` 的 helper（如果脚本数量增多）
  - **关键产出物**禁止仅靠 stdout，必须有 `--save-md` / `--save-json` 输出文件
